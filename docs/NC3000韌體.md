# NC3000 韌體分析筆記

這份文件記錄一份真機韌體（金遠見官方的 NC3000 仿真器附帶的映像）裡查到的事實：怎麼取出來、字型與圖形字放在哪裡（和我們現在用的 arucil 的 `res/` 差在哪裡）、時鐘位元組的排列，以及還沒查到的東西。**只記事實（位置、格式、數量、比較結果），不含任何字型資料或程式碼**；韌體本身有版權，只在本機分析，不放進專案。

## 怎麼取得（可重做）

1. 仿真器是一個 46 MB 的自解壓安裝程式（Delphi 做的 GPInstall）。不必執行它：後面接著的資料是一連串 LHA `-lh5-` 壓縮的檔案，每個檔案前面有這樣的標頭：名稱（`Program Files\檔名`）出現在位置 N，N−17 起 4 位元組是原始大小、N−13 起 4 位元組是壓縮後大小（小端），壓縮資料緊接在名稱之後。解出 `wqxsim.exe`（2.4 MB，仿真器本體）、`nd.bin`（61,400,064 位元組）、`obj.bin`（1 MB）和幾個小檔。
2. `nd.bin` 是**原始 NAND 傾印**：每頁 528 位元組 = 512 位元組資料 + 16 位元組備用區（ECC 與標記；絕大多數頁的備用區是 `FF`）。共 116,288 頁。把每頁的後 16 位元組去掉，得到 59,539,456 位元組的資料映像。**不去掉的話，每 512 位元組就插進 16 位元組垃圾，字型表會被切壞**（直接在 `nd.bin` 裡找字型找不到的原因）。
3. 以下所有位置都是「去掉備用區之後的資料映像」裡的偏移。

## 字型與圖形字表：位置與格式

| 內容 | 位置 | 格式 | 數量 | 和 arucil 的字型比較 |
|---|---|---|---|---|
| ASCII 8×16 | `0x4000` | 每字 16 位元組，字碼 0–159 | 160 | 159 個相同，只有 3 號不同 |
| ASCII 6×12 | `0x6200` | 每字 12 位元組，每列 1 位元組、左對齊 | 160 | 全部相同 |
| 漢字 16×16 | `0x18002` | 每字 32 位元組（每列 2 位元組，最高位在左）。**依 Unicode 排序**：U+4E00 的字形在 `0x18002`，之後每字 +32，到 U+9FA5（`0xBB4C2` 結束），之後填 `FF` 到 `0xBC000` | 20,902 | 沒有一個字逐位元組相同（比對 19 個兩邊都有的字）；字形較細、風格不同；**簡體與繁體字都有**（戰、鬥、惡、龍、時、錢、裝備…） |
| 漢字 12×12 | `0xBC000` | 每字 18 位元組：12 列 × 每列 12 位元，**列與列緊接、不補齊到位元組**，最高位在前。同樣依 Unicode 排序，U+4E00 在 `0xBC000`，到 `0x117DAC` | 20,902 | arucil 的 12×12 是每列 2 位元組（24 位元組），格式不同；也沒有找到相同的字 |

| 符號 12×12 | `0x124000` | 每字 18 位元組，和 16×16 符號表同一個排列，846 格，到 `0x127B7C`，再填 `FF` 到 `0x128000` | 846（159 格空白） | arucil 的 12×12 沒有拿來比 |

### 比較的結果與意義

- ASCII 兩張表和圖形字表**逐位元組相同**：arucil 的 `res/` 這三份確實是真機的資料，而且這台 NC3000 用的是同一份。
- 漢字、符號則是**另一套字型**（形狀相同、畫法不同）。arucil 的 16×16 漢字是 GB2312 排序、較粗；NC3000 的是 Unicode 排序、較細，而且涵蓋整個 CJK 統一漢字區（20,902 字），所以台灣用字（Big5）的繁體字都有字形。
- 以我們的需要來看：Big5（台灣機型）的程式，現在是用系統字型（MingLiU）畫字。Big5 碼可以先轉成 Unicode，再從這張表取字形，就得到真機風格的繁體字。**但這是有版權的真機資料**，不能像 arucil 的 `res/` 那樣直接放進專案，要做的話只能做成「使用者從自己的韌體取出、本機載入」的選用功能（這一步還沒做，也還沒決定）。
- 這份韌體是大陸機型（NC3000）。台灣機型的圖形字（Big5 `FA40` 以後的花色、圖塊）用的是**同一批 527 張圖**，只是編號不同（見 [圖形字編號.md](圖形字編號.md)）；NC3000 韌體本身怎麼處理 `FA40` 以後的碼，沒有查。

### 字型方面還沒查清楚的

- 圖形字之後那 131 格各是哪個字碼；以及 12×12 版本的圖形字放在哪裡（`0x128000` 起有一小段約 2.5 KB、`0x12C08E` 起還有資料，沒有辨認）。
- 韌體怎麼把 GB 碼／Big5 碼對應到 Unicode（應該有一張轉碼表）；字型表本身不需要它。
- 韌體的其他部分（BIOS、GVBASIC 解譯器的程式碼）還沒有看，只確認了 `nd.bin` 裡有 GVBASIC 的說明檔，內容和 `ref/help_utf8.txt` 相同，34 條錯誤訊息也一樣。
- `obj.bin`（1 MB）不含這些字型表，用途不明（開頭是 `60 EA`，後面接 `$A0xx` 的位址表，內文提到 NC3000）。

## 時鐘：`PEEK(1015)` 是小時

`obj.bin`（1 MB）是 6502 的作業系統 ROM：34 個 16 KB 的頁，每一頁開頭是 `60 EA` 加一張 `INT` 入口位址表（和《6502 編程大奧秘》講的 `INT $頁碼項目` 一致）。裡面有一段每次計時中斷都會跑的程式，把即時時鐘晶片（用零頁 `$3E` 選暫存器、`$3F` 讀寫）的暫存器抄進 RAM，並且負責日期進位。讀出來的排列：

| 位址 | 十進位 | 內容 | 依據 |
|---|---|---|---|
| `$03F7` | 1015 | **小時 0–23**（暫存器 2，遮罩 `$1F`） | 重設時預設寫入 12，也寫進暫存器 2 |
| `$03F8` | 1016 | 分鐘 0–59（暫存器 1，遮罩 `$3F`） | 預設 0 |
| `$03F9` | 1017 | 秒（暫存器 0，遮罩 `$3F` 之後**乘 2**，所以只會是偶數） | 預設 0 |
| `$03FA` | 1018 | 年 − 1881（閏年判斷把 19 當成 1900 年；到 `$97` 就繞回 `$33`） | 預設 `$7B` = 123 → 2004 |
| `$03FB` | 1019 | 月 0–11 | 進位表是 31,28,31,30,31,30,31,31,30,31,30,31 |
| `$03FC` | 1020 | 日 0–30 | 預設 0 |
| `$03FD` | 1021 | 星期 0–6，0 = 星期日 | 預設 4，2004-01-01 剛好是星期四 |
| `$03FE` | 1022 | 計時中斷的計數（0–119，每滿一圈歸零） | |
| `$03FF` | 1023 | 暫存器 4 的值，用途不明 | |

重設時的預設時間是 **2004-01-01 星期四 12:00:00**。結論：原本從程式用法推斷的「`PEEK(1015)` 是小時」得到韌體確認，同一排的 1016–1021 也有了定義。模擬器現在照這個排列回答 1015–1021（小時可以在側欄指定，其他取電腦的時間）。

## `PLAY`：這份韌體的 GVBASIC 裡它什麼都不做

`nd.bin` 裡的說明檔對 `PLAY` 只寫了 `PLAY "CDEFGAB"`，沒有音長、八度的說明；ROM 裡靜態找音符表（12 個半音的頻率／週期表、`O`／`L`／音名字母的比較指令、`CDEFGAB` 字串）都沒有找到。原因在後面「在真韌體上跑 GVBASIC」查到了：**在這份（大陸版 NC3000）韌體的 GVBASIC 裡，`PLAY` 的處理程式就是「`REM`」的處理程式**，所以沒有音符表可找。這個結論只適用於這份韌體；使用者原本那台（哈電族 NC3000，Big5）的韌體是另一個版本，不能直接套用。

## 讓韌體跑起來：自製的 NC3000 仿真（`tools/nc3000/`）

`tools/nc3000/` 是一個只讀資料、不執行任何第三方程式的 NC3000 仿真（6502 核心 + 硬體模型，約 600 行 JavaScript，**不含任何韌體**，用法見該資料夾的 README）。用上面取出的 `obj.bin` 與 `nd.bin`，真韌體已經能開機、顯示中文、讀鍵盤，一路走到主選單，英漢／漢英／AHD／劍橋辭典與 PDA 選單都能打開。以下是跑出來的事實；標「推測」的是沒有直接證據的部分。

### 記憶體與暫存器

- 重設向量 `$FFFC` 指到 `$FFF4`，那裡是 `JMP`；`$E0D2` 開始的重設程式最後 `JMP ($C002)`（開機表在 `$C000` 視窗）。
- `$0000–$003F` 是 I/O，`$0040–$3FFF` 是 RAM；`$4000–$BFFF` 是 32 KB 的 NOR 分頁視窗，分頁號在 `$00`，8 KB 小塊的排列順序是 +0x4000、+0x6000、+0x0000、+0x2000。分頁 0（沒有 ROA）的 `$4000–$7FFF` 是 RAM（作業系統核心開機時從 NOR 複製過去）；`$0A` 的最高位（ROA）打開時，分頁 0／1 的視窗改成 RAM（分頁 0 對應 RAM `$0000` 起，分頁 1 對應 `$8000` 起，應用程式載入後就在這裡執行）。`$C000–$DFFF` 由 `$0A` 的低 4 位選 8 KB（索引 1 = RAM `$6000`），`$E000–$FFFF` 固定是 NOR 的 `0x6000–0x7FFF`。
- 系統呼叫是 `BRK 服務號, 模組號`（和《6502 編程大奧秘》的 `INT` 一致）：模組號的低 4 位寫進 `$0A` 選視窗，服務號乘 2 去模組視窗開頭的位址表取程式位址。已確認的：模組 `$C7` 的服務 `$29` = 清除 LCD RAM；模組 5 是快閃檔案系統，服務 `$25` = 依路徑開檔、`$26` = 把檔案載入 `$4000`。
- 中斷：計時基礎 IRQ 每個畫面 4 次（`$05` 的 bit 2 打開、`$01` 的 bit 3 沒有被遮罩時才有），IRQ 程式讀 `$01`（讀取即清除）；「第二種來源」由 `$3D` 回報，我們在 IRQ 進入時鎖存：`$F8` = 沒有，`$00` = 韌體自己計數的慢速時鐘（推測是每秒 2 次：它數到 120 才進一位，`$0A24`／`$0A23` 看起來是分／時）。
- 鍵盤：韌體每次計時 IRQ 掃一行。把 `$09` 設成只有一個位元為 1（位元 7−c 選第 c 行），再讀 `$08`（列 7、6、5、4 在位元 7、6、5、4，列 0 在位元 0）和 `$1E`（列 3、2 在位元 1、0），按下的鍵讀成 0。掃描出來的碼表在 ROM `$ED05`（行 × 8 + 列），第 1 列全是 `FF`（保留）。字母鍵給小寫 ASCII，Enter = `$0D`，Esc = `$1B`，空白 = `$20`；其餘：列 0 的 `00 02 04 06 08 0A 0C` 是選單功能鍵（`06` 英漢／漢英、`08` AHD／詞庫、`0A` 劍橋／學習、`04` PDA／遊戲、`02` 計算／換算、`00` 時間／系統、`0C` 有聲學習／音樂），`18` = 關機；`25 26 27` 像是左上右；`1C–1F` 是 F4–F1。完整格子見 `tools/nc3000/keys.js` 讀碼表的方式。
- 計時器 `$02`／`$03` 是會一直走的計數器；重設後 `$02`、`$03` 不為零、且 RAM `$03E4 = $A5`、`$03E5 = $5A` 才算「熱啟動」（機器是睡著後被喚醒），否則是冷啟動。往 `$05` 寫 `$FF` = 待機，CPU 停住，按任何鍵由重設向量醒來（RAM 保留）。

### 快閃記憶體

- **NAND**：資料口 `$39`，控制 `$18`（bit 5 = CLE、bit 4 = ALE、bit 2 = CE）。命令 `00`／`01`／`50` 讀（前半、後半、備用區）、`80`…`10` 程式化、`60`…`D0` 清除、`70` 狀態、`90` 識別、`FF` 重設。讀與程式化送 4 個位址位元組（欄 + 3 位元組列），清除送 3 位元組列。每頁 528 位元組，每區塊 32 頁。
- **傾印與韌體列號差 64**：韌體用的列號 = `nd.bin` 的頁號 + 64。傾印的第一個區塊在備用區裡寫著區塊號 2（之後依序 3、4…），所以傾印**缺少韌體的前兩個區塊（列 0–63）**，也缺少最後 460 個區塊（3636–4095，修復時韌體自己把它們清掉）。少了這個 +64，系統修復一定失敗（第一版就卡在這裡）。列 1 補上 `ggv nc3000` 簽名頁，其餘空白，這和 WQXEmu 文件說的「沒有第一平面傾印時合成簽名」一致。
- **備用區**：每個區塊第一頁的 [0..1] = 區塊號（小端）；[6..8] 是 ECC，[9] = `AA` 標記，[13..15] 在每個區塊的最後一頁有 `30` 加 2 位元組。
- **NOR**：標準 AMD 指令集（`AA`／`55` 解鎖，命令位址 `$5555`／`$AAAA`，`A0` 寫入、`80`+`AA 55`+`30` 清除一個磁區、`F0` 重設），韌體實際用的清除單位是 4 KB。使用者區從 NOR 的 `0x88000` 到結尾（包裡全是 `FF`）；開機時韌體會在 `0x8C000` 寫一筆約 190 位元組的系統記錄，系統修復後在最後 64 KB（`0xF4000`）出現 `ggv nc3000` 簽名。寫入程式放在 RAM 裡跑（NOR 忙的時候不能從 NOR 取指令）。

### 開機流程（冷啟動，RAM 全空）

1. 「資料整理中，請稍候…」約 2 秒（這段是開機程式，此時中斷被遮罩，同時檢查 NOR 分頁 2、3、4 的校驗和）。
2. 作業系統核心起動，LCD 初始化，顯示問題「閃存中有數據，清除嗎？Y 清除，N 保留」（這是**每次冷啟動**都會問的，不是因為資料有問題）。
3. 按 N：「修復系統，請稍候」（約 2 秒，讀 NAND 的目錄資訊、重建 NOR 使用者區的表格、清掉傾印之外的區塊）→「系統校驗，請稍候…」→ 兩張 Logo（「文曲星 NC3000」、「英美權威雙授權」）輪流，按任何鍵進主選單。按 Y 則連問兩次確認（「數據將全部清除，是否取消操作」、「數據刪除後將無法恢復，確認嗎」）後格式化。
4. 主選單有 12 個圖示（英漢、AHD、劍橋、PDA、計算、時間／漢英、詞庫、學習、遊戲、換算、系統）。Esc 回選單；選單上的熱鍵會依路徑 `/sysdir/…` 載入程式。

### 檔案系統（看到的部分）

- 目錄項目是 16 位元組：2 位元組編號 + 以 0 結尾的 GBK 檔名。根目錄有 `..`（0）、`sysdir`（1）、`midi`、下載詞典、應用程式、旅遊全球話、歌曲音樂、文本文件等；`/sysdir` 的目錄清單（在傾印的 `0x31B8200` 附近）有 time、other、calculator、change、namecard、game、hero、txt_view、zijian、celps、jinqu、hexuan、xinhua 與 `xh_*`。ROM 裡有熱鍵 → 路徑表（`0x1D997` 起：`/sysdir/time`、`calculator`、`change`、`game`、`dict_yh`…，另有 `namecard`、`zijian`、`xinhua`、`txt_view`、`hexuan`、`jinqu`、`qmyj`、`celps` 等）。
- 熱鍵載入程式在 ROM `$E4E7`：`BRK $25,5`（依路徑開檔）→ `BRK $26,5`（載入到 `$4000`、最多 `$8000` 位元組）→ 用分頁 1 + ROA 從 `$4000` 執行。失敗時畫面是 `no load hot key` 加路徑，錯誤碼寫在 `$08CC`（2 = 找不到）。
- 大檔案的存放方式（觀察）：資料區塊（16 KB，每塊第一頁開頭是一張 `JMP` 位址表）連續排列，最後接一個「索引區塊」，內容是前面各資料區塊的區塊號（16 位元小端、遞增）。目錄資料頁的最後 8 位元組是 4 個 16 位元的尾註（下一個項目號、本頁列號、…、區塊總數 3636）。

| 聲音 | 只有蜂鳴器 `$18` 的位元 7（按鍵聲、`BEEP`）；`PLAY` 在這份韌體裡什麼都不做（見後面） |

### 檔案系統能用了：補上根目錄區塊

韌體要的根目錄資料放在區塊 3636（區塊號 `0x0E34`，根節點裡寫的就是這個），正好在傾印的後面，也正好是「修復系統」會清除的那一段，所以修復完以後根目錄是空的，`/sysdir` 找不到、所有熱鍵程式都載不進來。做法：把 NAND 擴成完整的 4096 區塊，修復完成後，把傾印第一個區塊的最後一頁（列 95，內容是 `..`、`sysdir`、`midi`、… 的根目錄清單）複製到區塊 3636 的第 0 頁（傾印頁 116288）。這之後熱鍵載入、資源管理器、BASIC 檔案都正常。這一步寫在 `tools/nc3000/sim.js` 的 `boot()`。

inode 的觀察：傾印第一個區塊（韌體區塊 2）的第 0–5 頁是 inode 表，每頁 16 筆、每筆 32 位元組（第一筆的編號是 1、`0x11`、`0x21`…），+0x0E 是檔案占的區塊數，+0x12 起是最多 4 個 16 位元的區塊號（超過就把最後一個換成「索引區塊」，索引區塊在資料區塊之後，裡面列出其餘區塊）。例：`change` = 區塊 `0x0C39`–`0x0C3F`（7 個，其中 `0x0C3C`–`0x0C3F` 由索引區塊 `0x0C40` 列出），`game` = `0x0C48`–`0x0C4E`。

## 在真韌體上跑 GVBASIC

這一節的結果都是用 `tools/nc3000/` 把官方 NC3000 的真韌體跑起來量到的。

### 怎麼進 BASIC、怎麼打程式、怎麼執行

- 主選單按「計算／換算」鍵（鍵碼 `02`）兩次進到計算選單；`15` `15`（下、下）翻到第二頁，`16` `16`（右、右）選到「BASIC」圖示，Enter。方向鍵是 `16` 右、`17` 左、`15` 下、`14` 上，`19` 是說明。問「創建新檔案 是(Y) 否(N)」，按 `y`，進入編輯器，行號自動給 10、20…（打一行按 Enter 換下一行）。
- 鍵盤上沒有數字鍵。編輯器的輸入模式用 `1A` 切換：字母 → 數字 → 拼音 → 回到字母；字母模式下 `12` 切換大小寫；數字模式下 `b n m`／`g h j`／`t y u` 是 1–9、`30` 是 0；字母模式下 `30` 打開符號表，九格用 `b n m g h j t y u` 選，`16` 翻頁：第 1 頁 `. , ; - / ? ! $ %`、第 2 頁 `( ) : ` ' " < > {`、第 3 頁 `} [ ] # ~ @ ^ & *`、第 4 頁 `+ = _ | \`。`tools/nc3000/basic.js` 把這些包成 `typer(s).type("PRINT \"HI\"")`。
- 打完按 Esc（「跳出」）：`1.保存文件`、`2.返回編輯`、`3.放棄保存`；選存檔後問檔名（檔名欄位只有字母，沒有數字模式），Enter 之後出現檔案清單，選到檔案按 Enter 就是**執行**；程式結束時畫面停住，Esc 回檔案清單。
- 解譯器本身是 `/sysdir/change` 這個檔案（七個區塊，`0x0C39`–`0x0C3F`）的前 32 KB，由熱鍵載入程式放進 RAM `$8000`（分頁 1 + ROA，CPU 看到的是 `$4000`），編輯器與執行器看起來是兩個疊在同一塊位址的模組（編輯階段與執行階段取的 RAM 內容，分派表不一樣；換入的動作沒有追蹤，這是推測）。

### `PLAY`：整行跳過，沒有聲音

執行階段的陳述式分派表在 `$61C3`（每項 2 位元組，是「位址 − 1」，用 `PHA`／`PHA`／`RTS` 跳過去，記號 = `$80` + 關鍵字序號）。查表的結果：

- `PLAY`（記號 `$A3`）的處理程式在 `$8825`，內容就是 `JMP $7742`，而 `$7742` 是 **`REM`** 的處理程式。
- 實測：`PLAY "C":PRINT "X"` 之後 `X` 沒有印出來——和 `REM` 一樣，整行（含後面用冒號接的語句）都被跳過。`PLAY "O4L8CDEFGAB"` 等執行時，蜂鳴器暫存器沒有任何寫入。
- `TRACE`、`NOTRACE`、`NORMAL`、`INVERSE`、`FLASH` 則各有一小段真的在改旗標的程式。

所以在這份韌體（大陸版 NC3000，也就是官方仿真器跑的那份）上，`PLAY` 不會發聲，也沒有音長、八度的規則可查。使用者那台哈電族 NC3000 的韌體是另一個版本，這個結論不能直接搬過去。

### `BEEP`：4.5 kHz、約 50 毫秒

- `BEEP`（記號 `$A4`）的處理程式在 `$8828`：後面沒有參數就 `JMP $E00F`（BIOS 的嗶聲）；有參數時轉到 `$679F`（推測是出錯，沒有驗證）。
- 蜂鳴器是零頁 `$18` 的位元 7；BIOS 的發聲程式在 `$E358`：先把時脈選擇設成 7 號（`$05` 的高 3 位元 = 3，全速），再用「寫 `$18` 位元 7 → 空轉迴圈 → 清位元 7 → 空轉迴圈」重複。
- 量到的 `BEEP`：半週期 1141.5 個 CPU 週期（週期 2283），共 515,200 個週期。時脈用 10.24 MHz（WQXEmu 對 NC3000 的說法；韌體開機和發聲時都選同一檔時脈）算：**4485 Hz、50.3 毫秒**。按鍵聲是另一個音：半週期 741.5、共 215,000 週期，約 6.9 kHz、21 毫秒。
- 計時 IRQ（每畫面 4 次）會打斷發聲程式，每次多花約 1,400 個週期，量測時要把這種空隙併進同一個音。（用 `tools/nc3000/run_program.js` 可以重做這個量測。）

### BASIC 的速度

在 `FOR I=1 TO 300:…:NEXT I` 裡，數解譯器每次執行 `NEXT` 之間的 CPU 週期（`tools/nc3000/loop_speed.js`；不用 `PRINT` 當記號，因為這份韌體的 `PRINT` 每次要花約 3.7 百萬週期，疑似在等計時，用它當記號量出來的數字會亂跳）：

| 迴圈內容 | 每圈週期數（中位數） | 毫秒（10.24 MHz） | 每秒圈數 |
|---|---|---|---|
| 只有 `NEXT I` | 2,325 | 0.23 | 4,400 |
| `B$="X"` | 4,686 | 0.46 | 2,200 |
| `A=A+1` | 6,758 | 0.66 | 1,500 |
| `A=I*2+3` | 8,922 | 0.87 | 1,150 |

每一圈除了 `NEXT` 還多一個賦值語句：賦值本身約 2,400（字串常數）到 6,600（有乘加的運算式）個週期，約 0.23–0.65 毫秒，也就是**每秒約 1,500–4,400 個簡單語句**，網頁模擬器預設的「每秒 3000 個語句」落在這個範圍內。這是 10.24 MHz 的假設下的數字；時脈若不同，數字等比例改變。

### 還沒做、還不確定的

- 時脈：沒有獨立證據證明解譯器執行時就是 10.24 MHz（只知道韌體在 BASIC 執行期間把 `$05` 設成 `$7C`，發聲時要求的是同一檔；待機時改成 `$1C`）。
- 語意驗證：`CLEAR`、`LSET`／`RSET`、`FIELD`／`PUT`／`GET`、`MKS$`、`NOT`、`RND`、數字格式、檔案錯誤名稱都已用真韌體量過並套用（見下節）；其他錯誤名稱（算術溢位、字串太長、陣列越界）還沒量。
- 時鐘不會走（RTC 暫存器沒有被推進），`PEEK(1015)` 一類的值目前固定。

## 語意驗證（進行中）：在真韌體上量到的

用 `tools/nc3000/run_program.js`（`PROG='行1|行2'`）跑小程式、看最後的文字畫面。以下都是實測；**還沒有套用到網頁模擬器的，標「待改」**。

- **賦值後面直接接東西**：`THEN`／`ELSE` 裡的賦值（`ELSE YS$="" GOTO 96`）後面的多餘部分連同那行剩下的（到 `ELSE` 或行尾）被丟掉、不報錯；在 `IF` 之外（`B$="" GOTO 30`、`A=1 PRINT "X"`）或接在 `PRINT`／`FOR`／`LOCATE` 後面則是 `?SYNTAX ERROR`。**已套用**（`MIDI EDITOR.BAS` 按音符鍵就會踩到）。
- **`NOT`、`AND`、`OR` 是邏輯運算，結果是 0 或 1**：`NOT 0` = 1，`NOT 5` = 0，`NOT -1` = 0；`6 AND 3` = 1，`6 OR 3` = 1，`0.5 OR 0` = 1。`NOT` 比 `+` 和比較運算結合得更緊：`NOT 1+1` = 1（即 `(NOT 1)+1`），`A=1:NOT A=1` = 0（即 `(NOT A)=1`）。`AND` 比 `OR` 優先（`0 AND 1 OR 1` = 1、`1 OR 0 AND 0` = 1），**和先前依 arucil 寫的「同一級、由左到右」不同，已套用到網頁模擬器**。
- **`CLEAR`**：變數清成 0、**DATA 指標歸零**（`DATA 1,2,3:READ A:CLEAR:READ B` 得 A=0、B=1），和我們一致（其餘效果見下）。
- **`MKI$`／`CVI$`**：低位元組在前（`MKI$(258)` = 2、1，長度 2）；`MKS$` 長度 5，`MKS$(1.5)` = 129、64、0、0、0（指數在前、尾數 4 位元組、最高位是符號，微軟 BASIC 格式）；`CVI$(MKI$(-2))` = -2、`CVS$(MKS$(-0.1))` = -.1。名稱要帶 `$`（`CVI`、`CVS` 沒有 `$` 會 `TYPE MISMATCH`）。數字印出時沒有前導空白、小數不補前導 0（`-.1`、`.738207502`）。
- **`RND` 是 Applesoft 一類的 5 位元組浮點數產生器，不是 16 位元的線性同餘**：種子在 RAM `$B8BB`（指數 1 位元組 + 尾數 4 位元組，最高位是符號）。`RND(x>0)`（不看 x）：種子乘 11879546（常數 `98 35 44 7A`，**第五個尾數位元組是下一個常數的第一個位元組 `68`**，所以尾數是 `B5 44 7A 68`）、加 3.92767778E-8（`68 28 B1 46`＋`20`；乘積的指數小的時候這個加法會改到最低的幾個位元，不能省）、尾數最高與最低位元組對調、舊指數位元組變成延伸位元組、指數設成 `$80`、正規化、依延伸位元組四捨五入後存回，回傳的就是這個值。乘法是逐位元累加（乘數從低位元組起、每個位元組 8 步，掉出 40 位元累加器的位元就丟掉）。`RND(0)` 回傳上一個值；`RND(-x)` 把 |x| 當作尾數來源，做同樣的對調、正規化、四捨五入，所以固定得到同一個數列。**已套用到網頁模擬器**：連續 59 步的種子位元組和韌體逐位元組一致，`RND(-1)` 後的 .738207502、.272707136、.299733446 與 `RND(-3)` 後的 .235586735、.186784665 也一致。沒有設種子時，起始種子是個整數（觀察到 5、85、91），每次開機不同，推測來自計時器。
- **數字印出的格式**（`PRINT`、`STR$`、`WRITE#` 都一樣）：9 位有效數字、去掉尾端 0、**小數不補前導 0**（`.5`、`-.1`、`.333333333`），0.01 到 999999999 之間印成一般小數，其餘用 E 記號、指數帶正負號和兩位數（`1E-03`、`1.5E+09`、`1.23456789E+09`、`1.09951163E+12`）；`0.1+0.2` 印成 `.3`。數字在韌體裡是 32 位元尾數的浮點數，所以第 9 位偶爾和雙精度不同（`3.14159265358979` 印成 `3.14159266`）。**已套用**（先前是 C 的 `%.9G`，印 `0.5`）。
- **`MKS$`**：**已套用**（見上；先前照 arucil 把指數放最後，和真機不同）。
- **`CLEAR` 的其餘效果**：`FOR` 迴圈中途 `CLEAR` 之後的 `NEXT` 是 `?NEXT WITHOUT FOR`、`GOSUB` 之後 `CLEAR` 再 `RETURN` 是 `?RETURN WITHOUT GOSUB`、`DEF FN` 被忘掉（`?UNDEF'D FUNCTION`）、陣列清成 0 可以重新 `DIM`、開著的檔案被關掉（之後 `LOF(1)` 是 `?FILE MODE ERROR`）。和網頁模擬器一致。
- **`LSET`／`RSET`**（隨機檔的欄位變數和一般字串變數相同）：`LSET` 把文字寫在變數的開頭，**剩下的字元保持原樣**（`A$` 是 `WXYZ`，`LSET A$="AB"` 得 `ABYZ`；空字串什麼都不改；太長就留前面的字元，`LSET A$="TOOLONG"` 得 `TOOL`），變數長度不變（`A$="ABCDEF":LSET A$="XY"` 得 `XYCDEF`）。`RSET` 則是**整個寬度重寫**：左邊補空格、文字靠右（`B$` 是 `WXYZ`，`RSET B$="CD"` 得 `  CD`；空字串得四個空格；太長一樣留前面的字元，`RSET B$="ABCDEFG"` 得 `ABCD`；一般變數 `A$="ABCDEF":RSET A$="XY"` 得 `    XY`）。`LSET A$=5` 是 `TYPE MISMATCH`。**已套用**（先前兩者都是「蓋在原字串上」，`RSET` 不補空格、太長時留後面的字元）。
- **`FIELD`／`PUT`／`GET` 是一塊記錄緩衝區**：`FIELD` 清空整塊緩衝區（含別的欄位變數管的位元組），欄位變數一開始是欄位寬度的零位元組（`LEN(A$)`=4、`ASC(A$)`=0）；每個 `FIELD` 敘述都從偏移 0 算起、先前的變數繼續存在，所以兩個 `FIELD` 敘述的變數會**共用位元組**（`FIELD #1,4 AS A$`、`FIELD #1,4 AS B$`、`LSET A$="WXYZ"` 之後 `B$` 也是 `WXYZ`）。對欄位變數**直接賦值**（`A$="XY"`）會讓它脫離緩衝區：`PUT` 寫的是緩衝區（所以不會寫進檔案）、`GET` 不會再改它（`A$="XY":PUT #1,1:GET #1,1` 之後 `A$` 還是 `XY`）；之後的 `LSET A$="Q"` 是對一般字串動手（得 `QY`）。`PUT` 沒有 `FIELD` 也可以（寫一筆零位元組）；沒有 `LEN` 或 `LEN=0` 時一筆記錄是 **32 位元組**；`FIELD` 總寬度超過記錄長度是 `?OUT OF DATA ERROR`；`LEN` 超過 255 是 `?ILLEGAL QUANTITY`；`PUT` 的記錄號為 0 或留空洞、`GET` 超過檔尾是 `?RECORD NUMBER ERROR`。檔案關掉再開，記錄還在。**已套用**（先前把欄位變數當成各自獨立的字串、`PUT` 直接寫變數的目前值、沒有 `LEN` 時記錄長度取欄位總寬度）。
- **檔案相關的錯誤名稱**：敘述（`WRITE #`、`INPUT #`、`GET`、`PUT`、`FIELD`，以及 `OPEN … AS #4`／`#0`）碰到沒開的檔案或模式不對的檔案，是 **`?SYNTAX ERROR`**（檔案號碼是在語法分析時查的）；函數 `LOF(n)`（只接受隨機檔）、`EOF(n)`（只接受 `INPUT` 檔）碰到沒開或模式不對是 **`?FILE MODE ERROR`**；`OPEN` 已經在用的號碼是 `?FILE OPEN ERROR`、`OPEN … FOR INPUT` 找不到檔案是 `?FILE NOT EXIST ERROR`、`CLOSE` 沒開的檔案是 `?FILE CLOSE ERROR`、`INPUT #` 超過最後一筆是 `?OUT OF DATA ERROR`。檔案號碼只有 1–3。`EOF` 為真時是 **1**（不是 -1），最後一筆讀完就為真。單獨一個 `CLOSE`（沒有 `#n`）是 `?SYNTAX ERROR`，網頁模擬器仍當成「關全部」（寬鬆，沒有改）。`PRINT #` 不是這份 BASIC 的語句（`?SYNTAX ERROR`），只有 `WRITE #`，網頁模擬器同樣不接受。**名稱已套用**（網頁版訊息在名稱後面可能多帶說明文字，如 `SYNTAX: FILE #1 NOT OPEN`）。
- **`PRINT` 對控制碼的處理**：`CHR$(0)` 和 `CHR$(31)` **不畫格子**、游標不動（`PRINT "AB";CHR$(0);"CD"` 顯示 `ABCD`；隨機檔的零位元組欄位印出來是空的，不是兩個空格寬）；`CHR$(1)`–`CHR$(30)` 各佔一格（文字區放進那個碼，`CHR$(10)`、`CHR$(13)` 也一樣是一格，不換行；畫出什麼圖形沒有看）。`LEN` 會把 `CHR$(0)` 算進去（`LEN("AB"+CHR$(0)+"C")` = 4）。**已套用**（先前 `CHR$(0)` 也佔一格）。
- **尚未量的**：`PRINT` 以外的畫面輸出對控制碼的處理（`LOCATE`、`INPUT` 提示）、其他錯誤名稱（算術溢位、字串太長、陣列越界、`DIM` 重複）。
